1 The Base Class (BasePage.js)

Foundation

The BasePage is the "Grandparent" class. It contains generic browser interactions that are NOT specific to any page.

Deep Dive: Every Word Explained

class BasePage { ... }

  • class: A blueprint for creating objects. It groups data and functions together.
  • BasePage: The name we gave this blueprint. "Base" implies it's a starting point for others.

constructor(page) { this.page = page; }

  • constructor: A special function that runs once when you create the page.
  • page (parameter): The actual browser tab provided by Playwright.
  • this.page: "this" refers to the current object. We are saving the browser tab so all other methods can find it.

async navigate(url) { await this.page.goto(url); }

  • async: Tells JavaScript this function takes time (it's "asynchronous").
  • url: The web address (e.g., 'https://google.com').
  • await: Tells the code to "Pause and Wait" until the website actually loads before moving to the next line.
  • goto: A built-in Playwright command to change the browser URL.

async fillInput(selector, text) { await this.page.locator(selector).fill(text); }

  • selector: The unique ID or XPath of the input field.
  • text: The data you want to type.
  • locator: Finds the exact element on the screen.
  • fill: Clears the field and types your text instantly.

async clickButton(selector) { await this.page.locator(selector).click(); }

  • click(): Simulates a mouse click on the element found by the locator.

async wait(seconds) { await this.page.waitForTimeout(seconds * 1000); }

  • seconds: How long you want the script to pause.
  • waitForTimeout: A built-in command that pauses the execution.
  • * 1000: Converts seconds to milliseconds (which is what Playwright understands).

module.exports = BasePage;

  • module.exports: The "Shipping Label". It allows other files (like SignupPage) to require and use this class.

Framework Dependencies

The BasePage is the "Parent" in the Page Object Model (POM). Its dependencies are:

  • Playwright Engine: It depends on the page object to talk to the browser.
  • Child Pages: SignupPage depends on BasePage to perform clicks and typing.
  • Tests: The spec.js files indirectly depend on it through the Page classes.

2 Page Classes (SignupPage.js)

Specialist

The SignupPage class extends BasePage. It inherits all methods from Step 1 and adds Page-Specific logic.

Deep Dive: SignupPage - Every Word Explained

const BasePage = require('./BasePage');

  • const: Declares a constant variable (one that won't change).
  • BasePage: The name we give to the imported parent class.
  • require: The command used to import code from another file.
  • './BasePage': The file path where the parent class is located.

class SignupPage extends BasePage { ... }

  • class: Tells JS we are defining a new blueprint.
  • SignupPage: The name of this specific blueprint.
  • extends: Links this class to BasePage (Inheritance).

constructor(page) { super(page); ... }

  • super(page): Transfers the browser page object to the Parent class so it can use it.
  • this.firstNameInput: Creates a property to store the XPath.
  • "//input[@name='...']": An XPath locator used to find the element on the HTML page.

async navigateToSignupForm() { await this.clickButton(...); }

  • navigateToSignupForm: The name of the action (User reaches the signup modal).
  • this.clickButton: Uses the clicking logic we defined in BasePage.

async fillBasicDetails(fName, lName, mobile) { ... }

  • fName, lName, mobile: Variable names for the data coming from the JSON file.
  • nextBtn: A temporary variable to hold the Next button element.
  • scrollIntoViewIfNeeded(): Ensures the button is visible on the screen before clicking it.
  • click(): The final command that triggers the page transition.

module.exports = SignupPage;

  • module.exports: Packaging the code so the Test file can use it.

3 Test Classes (signup.spec.js)

Execution

This is where the actual testing happens. It pulls everything together to run a scenario.

Deep Dive: Test File Explained

const { test, expect } = require('@playwright/test');

  • { test, expect }: Destructuring. We are taking only the test and expect tools from Playwright.
  • require('@playwright/test'): Importing the core Playwright library.

const signupData = require('../test-data/signupData.json');

  • signupData: The variable holding all the names, emails, and phone numbers from your JSON file.

test('Verify User...', async ({ page }) => { ... });

  • test('...'): Defines the start of a test case and its name.
  • ({ page }): This is called a Fixture. Playwright automatically gives you a fresh browser tab named page.

const signup = new SignupPage(page);

  • new SignupPage: Creates a live instance of your Page Class so you can call its methods.

signupData.newUser.firstName

  • .newUser.firstName: Navigates through the JSON layers to find the exact value "John".

try { await page.waitForNavigation(...) } catch (e) { ... }

  • try: "Try to do this action."
  • waitForNavigation: Wait for the website to move to a new page after clicking signup.
  • catch (e): "If it fails (timeout), don't crash the test. Just do what's in these brackets instead."

4 Test Data (signupData.json)

External Input

Instead of typing "John" directly in the code, we put it here. This is called Data-Driven Testing.

{
  "newUser": {
    "firstName": "John",
    "email": "john@example.com"
  }
}

The Test Class imports this using: const signupData = require('../test-data/signupData.json');

5 Selenium vs. Playwright: The Modern Evolution

You noticed a difference in how you used to write Selenium code versus this Playwright framework. Here is why the "Modern Way" is preferred in companies today:

Feature Traditional (Selenium) Modern (Playwright POM)
BasePage Role Mostly used for Browser Setup (initialising WebDriver, maximizing window). Used for Action Wrapping (creating reusable click/type methods).
Setup Logic Code is hidden in Java classes. Hard to change for different environments. Code is moved to playwright.config.js. Easy to switch browsers/headless via CLI.
Maintenance If a command changes, you fix it in every Page Class. If a command changes, you fix it in BasePage only.
Focus Focus on technical setup. Focus on business logic and readability.

💡 Pro Rationale:

In modern companies, we want the Test File to read like a story. By moving interaction logic into the BasePage, we ensure that the framework is "future-proof." If you ever need to add logging, screenshotting, or custom waits to every click, you do it in one single method in the BasePage!

6 The Data Handshake (Parameters vs Arguments)

How does the code know that fName means "John"? It's all about the Handshake between the Test File and the Page File.

1. The Sender (Test File)

await signup.fillBasicDetails(   "John", // 1st Argument   "Doe", // 2nd Argument   "12345" // 3rd Argument );

2. The Receiver (Page File)

async fillBasicDetails(   fName, // Placeholder 1   lName, // Placeholder 2   mobile // Placeholder 3 )

They "know" each other By Position (Order).

1st → 1st | 2nd → 2nd | 3rd → 3rd

9 The Life of 'page' and 'this'

Understanding how the browser tab (page) travels through your code is the "Secret Sauce" of this framework.

1. The Birth (signup.spec.js)

Playwright creates a fresh browser tab and hands it to the test:
test(..., async ({ page }) => { ... })

▼ Pass the baton

2. The Handover (Constructor)

You give that tab to your Page Class:
const signup = new SignupPage(page);

▼ Save it locally

3. The Ownership (this.page)

Inside BasePage, you save it as YOUR property:
this.page = page;

Note: "this" means "Me". So "this.page" means "My Page".

▼ Use it forever

4. The Action

Now, any method can use it to talk to the browser:
await this.page.goto(url);

8 Step-by-Step Argument Mapping

This table shows exactly how every piece of data is "mapped" from your JSON file to the website fields.

Step Argument (Real Data) Parameter (The Variable) The Target (XPath)
1 signupData.newUser.firstName fName this.firstNameInput
2 signupData.newUser.lastName lName this.lastNameInput
3 signupData.newUser.mobileNumber mobile this.mobileInput

Critical Rule: The computer doesn't care about the name fName. It only cares that it is the 1st word in the brackets. If you put mobileNumber as the 1st argument in the test file, it would be saved into the fName variable! Order is everything.
